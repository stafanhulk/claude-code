# Sediment +extract：从对话中提取候选条目

`+extract` 用于解决"沉淀的最大障碍是懒得写"的问题：让 AI 扫描当前会话，自动识别值得沉淀的内容，分类后请用户确认再落盘。

---

## 一、扫描范围

只扫描**当前会话窗口**内的对话内容，不读 git 历史、不读其他 session 文件。重点关注以下信号：

| 信号 | 说明 | 默认归类 |
|------|------|----------|
| 用户说 "不对/不是这样/应该 X 而不是 Y" | 纠正性反馈 | `how-to-write` |
| 用户说 "这个之前踩过坑/上次也是这样/又来了" | 重复出现的故障 | `how-to-debug` |
| 用户解释了"为什么这里要这么写" | 隐藏约束 | `how-to-write` |
| 用户解释了"为什么选 X 不选 Y / 为什么这么设计" | 架构决策 | `how-it-works` |
| 用户介绍了某个操作的步骤（部署 / 本地起服务 / CI） | 操作流程 | `how-to-run` |
| 用户介绍了项目里的术语、状态、外部系统 | 领域知识 | `what-it-means` |
| 调试中找到根因并修复 | 修过的具体 bug | `how-to-debug` |

## 二、过滤准则（严格执行）

**拒绝**以下内容，绝不进入候选：

- 用户的口头表达、情绪、调侃
- 通用编程知识（"async 函数要 await"、"setInterval 要 clearInterval"）
- 当前任务的临时上下文（"这次我们要修 xxx 文件"）
- 显而易见、看代码就知道的事（"这个组件用了 Vue"）
- 仅一次性出现、未确认是规律的现象

如果筛完没有合格候选，直接告诉用户"本次会话中没有发现值得沉淀的内容"并停止，不要凑数。

## 三、提取流程

### Step 1：扫描并打草稿

按上面信号逐条提取，每条内部草稿格式：

```
[草稿 #N]
分类：{how-it-works | how-to-write | how-to-run | how-to-debug | what-it-means}
标题：{简短标题，≤ 20 字}
内容：{按对应模板填写各字段}
信号来源：{摘录 1-2 句对话原话}
```

### Step 2：呈现给用户确认

用带 **`#N` 序号前缀**的列表展示所有候选，每条只展示**序号 + 分类 + 标题 + 一句话摘要**，不展开模板细节。**序号是用户后续选择的唯一引用方式，必须从 #1 开始连续编号，且与 Step 1 草稿中的 #N 保持一致。**

```markdown
本次会话提取到 N 条候选：

#1  [how-to-debug]  Pinia store 在 SSR 下被串数据
    ↳ 来自调试 "用户 A 看到 B 的信息" 的根因

#2  [how-to-write]  金额字段必须用 decimal.js
    ↳ 来自你纠正 "不要用 number 算价格"

#3  [how-it-works] 前端状态拆分为 server-state / ui-state
    ↳ 来自你说"为什么不全用 Redux"

请按序号选择要保留的条目：
  - 单选：#1
  - 多选：#1,#3 / 1,3 / 1 和 3
  - 范围：#1-#3
  - 全部：all / 全部
  - 取消：none / 都不要
  - 按分类：only how-to-debug
  - 改写：#1 改分类为 how-to-write / #2 改标题为 ...
```

### Step 3：等待用户回复

**绝对不允许**用户未明确确认就写入。常见回复模式：

| 用户回复 | 处理 |
|----------|------|
| `#1,#3` / `1,3` / `1 和 3` | 写入序号 1、3 |
| `#1-#3` / `1-3` | 写入序号 1 到 3 |
| `all` / `全部` / `都要` | 写入全部 |
| `none` / `都不要` / `算了` | 终止，不写任何东西 |
| `only how-to-debug` / `只要 how-to-debug` | 写入分类为 how-to-debug 的全部候选 |
| `#1 改分类为 X` / `保留 #1，但改成 X 分类` | 按修改后写入 #1 |
| `除了 #2` / `去掉 2` | 写入除 #2 外的全部候选 |

模糊回复（如"看着办" / 没有序号引用）→ 反问，不替用户做决定。

**解析顺序**：先识别"全部 / 都不要"等终止指令；再尝试匹配序号（`#N` 或纯数字 N）；最后匹配分类过滤词。任何无法解析的回复都视为模糊回复。

### Step 4：逐条写入

对确认要保留的每一条，按 [`sediment-categories.md`](sediment-categories.md) 的"+save 执行步骤"流程写入（含去重检查 + 评分调整）。

呈现候选时若该候选命中已有条目，**必须显示当前评分并询问用户**：

```
候选 #2 [how-to-write] 金额字段必须用 decimal.js
  ↳ 已存在同名条目（score: 2, hits: 3, last_hit: 2026-04-12）
  请选择：1=确认重复（score+1）/ 2=合并新信息（score+1）/ 3=覆盖（旧条目归档，新条目 score=1 起算）/ 4=跳过
```

绝不允许 AI 在用户未选择时自动调分。

### Step 5：汇总输出

```
[沉淀] 本次共写入 N 条新条目：
  - [how-to-debug] Pinia store 在 SSR 下被串数据 (score: 1)
  - [how-it-works] 前端状态拆分为 server-state / ui-state (score: 1)
[强化] M 条已有条目命中并 +1 分：
  - [how-to-write] 金额字段必须用 decimal.js (score: 2 → 3)
[索引] .ai-sediment/INDEX.md 已更新
```

## 四、`/sediment <自由内容>`（带内容版）的特殊处理

当用户调用 `/sediment <一段自由文字>`（既没有 `+save` 也没有 `+extract` 子命令），将这段文字作为**唯一候选**喂入本流程：

1. 跳过 Step 1 的会话扫描，直接进入 Step 2。
2. AI 判断分类（按 [`sediment-categories.md`](sediment-categories.md) 的"分类判定决策树"）。
3. 展示：

   ```
   建议分类：{X}
   建议标题：{Y}
   是否写入？(y / 改分类 / 改标题 / 取消)
   ```

4. 用户确认后按模板写入。

## 五、防滥用约束

- **单次会话最多提取 5 条**。超过 5 条说明信号不够精准，应让用户手动 `+save`。
- **同一条信号不重复呈现**：如果两个候选实际指向同一规则，合并为一条。
- **AI 不能自我引用**：不要把"AI 之前回答过 X"作为信号，只采纳用户提供的信息。
