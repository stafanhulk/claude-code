# Design

**CRITICAL — 生成方案前 MUST 先调研相关代码（按线索定位 + 逐文件 Read），禁止凭想象设计。优先复用现有函数 / 工具 / 模式，不重复造轮子。**
**CRITICAL — 方案中引用的现有代码 MUST 标 `文件:行号` 且确认真实存在；禁止编造不存在的接口、工具或函数。**
**CRITICAL — 复杂度判断 MUST 显式做：识别出 ≥2 个关键决策点（有多种合理实现且取舍不同）时，先把选型 + 取舍列给用户拍板，禁止 AI 替用户默默选定后直接展开。**
**CRITICAL — 方案 MUST 有清晰逻辑链条：从需求 → 现状 → 设计决策 → 各情况处理 → 影响范围，环环可推导。任何一环不清晰或不明白，MUST 用 AskUserQuestion 提问澄清，禁止靠猜测、含糊带过或先写个"大概方案"凑数。搞懂后才能产出完整方案。**
**CRITICAL — 写入文件属落盘操作；目标文件已存在时 MUST 先提示用户选 覆盖 / 更新 / 仅预览，禁止直接覆盖。**
**CRITICAL — 范围克制：只设计用户要的需求，禁止顺手设计未来需求或扩大改动面。**

## 调用方式

```
/design <需求描述 | 需求文档.md>        # 等价 +new
/design +new <需求描述 | 需求文档.md>   # 调研代码 + 生成方案文档（落盘）
/design +update <文件>                  # 基于最新代码更新已有方案文档
/design +preview <需求描述 | 需求文档.md>  # 只在对话中预览方案，不写文件
/design +new <需求> --out <文件>        # 指定输出路径（默认 docs/design/{主题}.md）
```

| 参数 | 说明 | 默认值 |
|------|------|--------|
| `<需求描述>` | 要设计的需求 / 改动意图。可以是**一段文字**，也可以是**一个 `.md` 需求文档路径**（便于管理需求） | 必填 |
| `<文件>` | `+update` 的目标方案文档路径 | 必填 |
| `--out <文件>` | 指定方案输出路径 | `docs/design/{主题}.md` |

## Shortcuts

| Shortcut | 说明 |
|----------|------|
| `+new <需求>` | 完整流程：调研代码 → 确认边界 → 复杂度判断 → 生成方案并落盘 |
| `+update <文件>` | 读已有方案 + 重新调研代码，更新已变化的章节 |
| `+preview <需求>` | 调研 + 生成方案草稿，只在对话展示，不落盘 |

## 执行流程

### Step 0：入参解析

**先判断需求来源**：入参是否指向一个存在的 `.md` 文件？

- **是文件路径** → MUST 先用 Read 读取该需求文档，以其内容作为需求；主题默认取文档标题 / 文件名。
- **是文字描述** → 直接作为需求。

```bash
# 判断入参是否为 md 需求文档
[ -f "<入参>" ] && case "<入参>" in *.md) echo "需求文档";; esac
```

从需求内容提取两件事：

- **需求主题**：一句话概括要做什么，用于默认文件名 `docs/design/{主题}.md`（kebab-case）。
- **范围线索**：需求涉及哪些模块 / 文件 / 功能，作为 Step 1 调研的起点。

路由（入参为文字或 `.md` 文档路径均适用）：

| 用户输入 | 路由到 |
|----------|-------|
| `+new <需求>` 或 `/design <需求>` | 完整流程 Step 1 → Step 5 |
| `+preview <需求>` | Step 1 → Step 4，Step 5 只输出到对话，不落盘 |
| `+update <文件>` | 先 Read 该文件，再重新走 Step 1 调研，更新已变化章节 |

### Step 1：调研代码

**CRITICAL — 进入本步 MUST 先用 Read 读取 [`references/design-workflow.md`](references/design-workflow.md)，按其中的调研套路执行。**

按范围线索定位相关代码，逐文件 Read，提炼四件事：

1. **现状如何工作** — 相关流程现在怎么跑通，关键 `文件:行号`。
2. **可复用能力** — 已有的同类实现、公共工具、现成 hook / 基类（标 `文件:行号`），方案应优先复用。
3. **约束与坑** — 不变量、隐式假设、改动会牵连的地方。
4. **影响范围** — 改动会牵连哪些调用方 / 下游 / 共享状态 / 对外契约（标 `文件:行号`）。复杂方案的不同选型影响范围不同，分别评估。

范围不清时先用 `find` / `grep` 定位再读，禁止只凭文件名推断。

### Step 2：需求与边界确认（澄清到逻辑链条通顺为止）

**目标：在设计前把逻辑链条打通——需求意图、边界 case、隐含约束、各分支的预期行为都清楚，能从需求推导到实现。**

调研后逐条自检，凡是以下情况 MUST 用 AskUserQuestion 提问，**禁止猜测或含糊带过**：

- 需求意图有歧义，或存在多种合理理解。
- 边界 / 异常 case 的预期行为未知（如空数据、超长、并发、多组取哪组）。
- 交互 / 状态流转有未覆盖的分支。
- 依赖的前提、约束、外部契约不确定。

提问可分多轮，直到逻辑链条无断点。**搞懂后才进入 Step 3**；需求确实无歧义则跳过本步。

### Step 3：复杂度判断与选型（自适应核心）

按 [`references/design-workflow.md`](references/design-workflow.md) 的「复杂度判断规则」识别关键决策点：

- **简单**（单一合理实现，无关键决策点）→ 直接进入 Step 4，出单一推荐方案。
- **复杂**（识别出 ≥2 个关键决策点）→ 先把每个决策点的「选项 / 取舍 / 推荐」用 AskUserQuestion 或文字列出，**等用户拍板后**再进入 Step 4 展开选定方案。

纯实现细节不算决策点，不要为凑数硬列。

### Step 4：生成方案文档

**CRITICAL — 进入本步若未读过 [`references/design-doc-template.md`](references/design-doc-template.md)，MUST 先 Read。**

按模板结构写，核心是**层级树 + 分支枚举**：方案设计像一棵树——功能点（`###`）→ 有序子点（`1. 2.`）→ 分支 / 细节（缩进 `-`）。互斥分支用 `**【条件】**：行为 → 结果` 标注，条件列全。一层一句短句，靠缩进表达从属，忌长段落和啰嗦。所有现有代码引用标 `文件:行号`。

### Step 5：落盘

默认写入 `docs/design/{主题}.md`（目录不存在则 `mkdir -p` 创建）。

- 文件已存在 → 提示用户选 覆盖 / 更新 / 仅预览，禁止直接覆盖。
- `+preview` → 只输出到对话，不写文件。

写入完成输出：

```
[方案] 已生成：{输出路径}
       需求：{主题}  调研文件数：{N}  形态：{单一方案 / 多方案选型}
```
