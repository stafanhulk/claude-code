# 方案文档模板

输出文件：`docs/design/{主题}.md`（或 `--out` 指定路径）。

核心风格：**清晰分支 + 情况枚举**。不依赖画图，用「情况 A / 情况 B」逐一讲清每个分支。

---

```markdown
# {需求主题} 技术方案

> 生成于 {YYYY-MM-DD} · 调研文件数 {N}

## 方案设计

{核心章节。功能点用编号组织成层级树。现状、决策结果就近内联到相关功能点，不单列大章节。验证与影响范围另立章节（测试同学关注区）。}

### 1. {功能点，如 题目渲染}

> 现状：{一句话，标 `文件:行号`}；复用 `{文件:行号}` 的 {函数/组件}。

1. {子点，一句话说清}，见 `{文件:行号}`
2. {子点}
   - {更细的说明或分支}

### 2. {功能点，如 交互}

> 决策：{有关键决策点时，一句话写选定结论，不写对比过程}。

1. {子功能点，如 触摸生命周期}
   - {行为规则，短句}
2. {子功能点，如 路径选择}，分支用【条件】标：
   - **【{条件 A}】**：{行为} → {结果}
   - **【{条件 B}】**：{行为} → {结果}
3. {子功能点，含嵌套分支}
   - **【{条件}】**：{处理}
     - **【{子条件}】**：{处理}
     - **【{子条件}】**：{处理}

## 改动清单

{要改 / 新增哪些文件，每条注明动作和参考的现有写法。}

- **新增** `{文件}`：{做什么}，参考现有写法 `{同类文件:行号}`
- **修改** `{文件:行号}`：{改什么}

## 测试关注

> 以下与开发实现关系不大，供测试同学关注。

**影响范围**（改动会牵连到哪些地方，每条标 `文件:行号` 或模块）：

- **直接改动**：{被本方案直接修改/新增的文件}
- **调用方 / 下游**：`{文件:行号}` 依赖了被改部分，需同步确认是否受影响
- **共享状态 / 数据**：{改动的数据结构、store、接口被谁共用}
- **跨端 / 跨模块**：{是否影响其他端、其他模块、对外接口契约}

**验证**（怎么测，每条写「输入 → 预期」，覆盖正常 + 边界 + 异常）：

- **{功能点 / 场景}**
  - {正常输入} → {预期}
  - {边界输入} → {预期}
  - {异常输入} → {预期}

> 找影响范围的命令见 design-workflow.md 第 1 节。
```

## 层级与分支写法（核心）

方案设计像一棵**层级树**：功能点（`###` 标题）→ 有序子点（`1. 2.`）→ 分支 / 细节（缩进的 `-`）。每层只写一句短句，靠缩进表达从属，不写长段落。

**分支必须用【条件】标注**，格式 `**【条件】**：行为 → 结果`；条件互斥时（是/否、对/错、有/无）逐条列全，嵌套分支再缩进一层。

**反例**（长段落 + 笼统，编码时仍要猜）：

```
拖拽单词到空格时会根据目标空格的状态决定是填入还是替换，如果拖到非空格区域则退回。
```

**正例**（层级树 + 分支清晰，可直接照做）：

```
### 2. 交互

1. 触摸结束时记录路径
   - 当前路径 < 2 个格子 → 不记录
2. 拖拽选项区单词到空格
   - **【目标空格为空】**：直接填入 → 选项区移除该词
   - **【目标空格已有单词】**：两词交换 → 原词退回选项区
   - **【拖到非空格区域】**：不接受 → 单词回弹原位
```

## 写法要求

- **层级树表达**：功能点用 `###` + 编号（`1.` `2.`），子点用有序列表，分支 / 细节用缩进 `-`；靠缩进表达从属，一层一句短句，不堆长段落。
- **分支用【条件】**：互斥分支写成 `**【条件】**：行为 → 结果`，条件列全（是/否、对/错、有/无），嵌套再缩进。
- **一句一事，忌啰嗦**：能一句说清就不写两句；说明性文字压到最少，让层级和分支自己说话。
- **信息就近内联**：现状、决策结果不单列大章节，用引用行（`>`）贴到相关功能点，能省则省。
- **测试关注独立成章**：影响范围 + 验证合并为文档末尾的「测试关注」章节，与开发实现关系不大，不散在方案设计里。
- **逻辑链条要闭合**：现状 → 决策结果 → 各情况处理 → 影响范围，读者能顺着推导，不出现"为什么这么设计"无法回答的断点。任何一环不清楚，先提问澄清再写，不靠猜测填空。
- **现有代码引用标 `文件:行号`**，确保真实存在，方便编码时跳转。
- **可复用能力优先**：功能点内联指出能复用的现有函数 / 工具，方案直接引用，不重复造。
- **改动清单要具体**：写到「在哪个文件做什么动作、参考哪个现有写法」，不写「参考现有代码」这种空话。
- **验证写输入与预期**，覆盖正常 + 边界 + 异常。

## 不写什么

- 通用编程知识、语言语法说明。
- 与需求无关的周边重构建议。
- 凭空捏造、未在代码中确认存在的接口或工具。
- 未来需求的设计（超出本次范围）。
