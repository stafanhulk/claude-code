# 方案文档模板

输出文件：`docs/design/{主题}.md`（或 `--out` 指定路径）。

核心风格：**清晰分支 + 情况枚举**。不依赖画图，用「情况 A / 情况 B」逐一讲清每个分支。

---

```markdown
# {需求主题} 技术方案

> 生成于 {YYYY-MM-DD} · 调研文件数 {N}

## 背景与目标

{为什么做这个需求、要达成什么。}

- **目标**：{要解决的问题 / 要实现的能力}
- **不做**：{明确划出范围边界，本次不涉及的部分}

## 现状

{相关代码现在怎么工作，作为方案的事实基础。}

- {关键流程描述}，见 `{文件:行号}`
- **可复用**：`{文件:行号}` 已有 {函数/工具/hook}，方案直接复用，不重写

## 关键决策

> 仅复杂方案（≥2 个关键决策点）保留本章节；单一方案删除。

### 决策 1：{决策点名称}

| 选项 | 优势 | 劣势 | 影响范围 |
|------|------|------|---------|
| 方案 A | … | … | {改动牵连的模块/文件/调用方，A 和 B 通常不同} |
| 方案 B | … | … | … |

**选定**：{用户拍板的结论 + 理由}

## 方案设计

{核心章节。按功能点分层标题组织，每个功能点把各种情况逐一枚举。}

### {功能点 1}

{整体说明。}

- **情况 A：{触发条件}** → {行为} → {结果}
- **情况 B：{触发条件}** → {行为} → {结果}
- **边界 / 异常：{条件}** → {如何处理}

### {功能点 2}

{...}

## 改动清单

{要改 / 新增哪些文件，每条注明动作和参考的现有写法。}

- **新增** `{文件}`：{做什么}，参考现有写法 `{同类文件:行号}`
- **修改** `{文件:行号}`：{改什么}

## 影响范围

{本方案改动会牵连到哪些地方。按"直接改动 → 间接影响"两层列，每条标 `文件:行号` 或模块。}

- **直接改动**：{被本方案直接修改/新增的文件}
- **调用方 / 下游**：`{文件:行号}` 依赖了被改部分，需同步确认是否受影响
- **共享状态 / 数据**：{改动的数据结构、store、接口被谁共用}
- **跨端 / 跨模块**：{是否影响其他端、其他模块、对外接口契约}

> 找影响范围的命令见 design-workflow.md 第 1 节。复杂方案的不同选型，影响范围通常不同，已在「关键决策」表中对照列出。

## 风险与验证

- **风险**：{改动可能牵连的地方 / 隐患}
- **验证**：{怎么测——跑什么命令、手动验证哪些 case}
  - 验证 case 1：{输入 → 预期}
  - 验证 case 2：{边界输入 → 预期}
```

## 情况枚举写法（核心）

方案设计章节的每个分支必须写成「触发条件 → 行为 → 结果」三段，不要只写一句模糊描述。

**反例**（太笼统，编码时仍要猜）：

```
拖拽单词到空格时会填入或替换。
```

**正例**（分支清晰，可直接照做）：

```
### 拖拽选项区单词到空格

- **情况 A：目标空格为空** → 单词填入该空格 → 选项区移除该词，空格显示填入态
- **情况 B：目标空格已有单词** → 两词交换 → 原空格词回退到选项区，新词填入
- **边界：拖拽到非空格区域** → 不接受 → 单词回弹到原选项位置
```

## 写法要求

- **逻辑链条要闭合**：需求 → 现状 → 决策 → 各情况处理 → 影响范围，读者能顺着推导，不出现"为什么这么设计"无法回答的断点。任何一环不清楚，先提问澄清再写，不靠猜测填空。
- **现有代码引用标 `文件:行号`**，确保真实存在，方便编码时跳转。
- **可复用能力优先**：现状章节明确列出能复用的现有函数 / 工具，方案设计直接引用，不重复造。
- **改动清单要具体**：写到「在哪个文件做什么动作、参考哪个现有写法」，不写「参考现有代码」这种空话。
- **验证 case 写输入与预期**，覆盖正常 + 边界 + 异常。

## 不写什么

- 通用编程知识、语言语法说明。
- 与需求无关的周边重构建议。
- 凭空捏造、未在代码中确认存在的接口或工具。
- 未来需求的设计（超出本次范围）。
