# 设计工作流：调研 + 复杂度判断 + 取舍呈现

本文档供 SKILL.md 的 Step 1 与 Step 3 按需读取。

---

## 1. 调研怎么做（Step 1）

**目标：在动笔设计前，把现状、可复用能力、约束摸清楚。禁止凭想象。**

### 定位相关代码

按范围线索从入口往下查。线索不明确时先搜：

```bash
# 按功能关键词搜实现位置
grep -rn "{关键词/函数名/组件名}" {项目根}/ --include="*.{ext}" \
  ! -path "*/node_modules/*" ! -path "*/dist/*"

# 找某类同类文件（用于推断扩展模式）
find {项目根} -type f -name "*{类型后缀}*" ! -path "*/node_modules/*"
```

### 逐文件 Read 优先级

1. **入口 / 调用方**：需求从哪里被触发，理解上下文。
2. **类型定义**：数据结构决定方案形态，先看 `types`、`interface`、`model`。
3. **核心逻辑**：现状怎么实现的，关键 `文件:行号`。
4. **同类已有实现**：有没有相似功能已经做过，照它的模式做最省事。
5. **测试**：理解预期行为和已覆盖的边界。

### 提炼「可复用能力」

设计前 MUST 找一遍能复用的东西，避免重复造：

- **同类实现**：已有相似功能 → 照同样模式做，方案里直接引用其 `文件:行号`。
- **公共工具 / hook / 基类**：`utils/`、`hooks/`、`base/` 下现成的，方案直接调用。
- **现有数据结构 / 接口**：能扩展的就扩展，不另起炉灶。

调研产出喂给方案的「现状」章节，可复用项必须标 `文件:行号`。

### 找影响范围

设计前 MUST 确认改动会牵连哪些地方，喂给方案的「影响范围」章节。复杂方案的不同选型，影响范围往往不同，要分别评估。

```bash
# 谁 import 了将被改的文件（找直接调用方）
grep -rn "from '.*{目标文件相对路径}'" {项目根}/ --include="*.{ext}"

# 谁引用了将被改的函数 / 组件 / 类型名（找下游使用点）
grep -rn "{函数名/组件名/类型名}" {项目根}/ --include="*.{ext}" \
  ! -path "*/node_modules/*" ! -path "*/dist/*"
```

按两层归纳：

- **直接改动**：本方案会动哪些文件。
- **间接影响**：调用方 / 下游、共享的 store 或数据结构、对外接口契约、跨端跨模块。逐个 Read 确认是否需要同步改，标 `文件:行号`。

## 2. 复杂度判断规则（Step 3）

**判断方案是「单一推荐」还是「先列选型」，取决于有没有关键决策点。**

### 什么算「关键决策点」

满足以下全部才算：

1. 有 **≥2 种合理实现**（不是一对一错，是各有取舍）。
2. 不同选择会**显著影响**架构、数据结构、性能或后续扩展。
3. 取舍**用户应该知情并拍板**，而非纯技术细节。

典型关键决策点：

- 数据结构选型（用数组还是 Map、扁平还是嵌套）。
- 逻辑放哪一层（判题在前端还是后端、校验在哪做）。
- 状态管理方式（本地 state / 全局 store / context）。
- 复用现有模块 vs 新建模块。
- 同步 vs 异步、实时 vs 轮询。

### 什么不算（不要硬列）

- 变量命名、函数拆分粒度这类纯实现细节。
- 只有一种合理做法、另一种明显更差的「伪选项」。
- 不影响外部行为、编码时随手就能定的细节。

### 判定结果

- **0 个关键决策点** → 简单，直接出单一推荐方案。
- **≥2 个关键决策点** → 复杂，先列选型让用户拍板。
- **恰好 1 个** → 看权重：影响大就列出来确认，影响小就在方案里直接采用并注明理由。

## 3. 取舍呈现规则（Step 3）

识别出关键决策点后，每个决策点呈现给用户时写清三件事：

| 要素 | 要求 |
|------|------|
| **选项** | 列出 2-3 个合理实现，各起个清晰名字 |
| **取舍** | 每个选项的优势 / 劣势，对照写，不含糊 |
| **推荐** | 给出推荐选项 + 理由，但**由用户拍板**，不替用户定 |

用 AskUserQuestion 让用户选，或文字列出等用户回复。**禁止 AI 自己选定后直接展开方案。**

用户拍板后，把结论写进方案文档的「关键决策」章节，方案设计章节按选定结果展开。

---

## 4. 不写什么

- 通用编程知识、语言语法。
- 与本次需求无关的周边重构。
- 凭空捏造、未在代码中确认存在的接口 / 工具 / 函数。
- 超出本次需求范围的未来设计。
