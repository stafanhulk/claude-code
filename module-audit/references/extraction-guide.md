# 代码提炼指南

阅读模块源码时，只提炼以下四类信息，其他内容不写入文档。

---

## 1. 核心约束

**提炼目标：** 模块中必须被保留的不变量——破坏它会导致功能错误、类型失效或隐式假设被违反。

**如何识别：**
- 防御性检查（if 判断 + throw/return early）出现在多个入口，说明有强制前置条件
- 注释中出现 "must"、"always"、"never"、"required"
- 某个函数被所有同类流程调用，说明它是不可绕过的公共路径
- 类型断言（`as Type`、`!`）前没有校验，说明上游有隐性保证

**写法要求：**
- 写成"动作 + 后果"格式："{必须做 X}，否则 {Y 会发生}"
- 每条附 `文件:行号` 作为可核实的依据
- 不写建议，只写必须遵守的规则

**示例：**
```
- `validator.ts:12` — 所有外部输入必须经过 `validateInput()` 处理，绕过会导致 `processor.ts` 中的类型断言失败
- `store.ts:45` — 写操作必须通过 `dispatch()` 发起，直接修改 state 会绕过订阅者通知
```

---

## 2. 设计意图

**提炼目标：** 从代码结构中推断出的模块组织思路，帮助后续开发者保持风格一致。

**如何识别：**
- 目录分层是否体现某种职责划分（IO 与逻辑分离、入口与实现分离）
- 相同类型的文件是否遵循统一结构（都有相同的函数签名、都实现同一接口）
- 某种写法在全模块高度一致，说明是有意为之的约定

**写法要求：**
- 用一到两段话描述，不用列表
- 说明"分工是什么"以及"为什么新代码要遵循这个分工"
- 只写能从代码结构中观察到的意图，不推断未见过的设计

**示例：**
```
该模块将数据获取与业务逻辑严格分层：fetcher 层只负责 IO，不含任何业务判断；
transformer 层只做数据变换，不发起任何请求。新增功能时应遵循这一分工，
在 transformer 中引入 IO 会破坏现有的测试隔离策略。
```

## 3. 扩展路径

**提炼目标：** 新增某类功能时的具体操作步骤，基于模块中现有的真实例子推导。

**如何识别：**
- 找模块中同类文件最多的那一类（handler、service、model 等），观察它们的共同结构
- 追踪一个现有同类功能从创建到注册的完整路径，记录每一步涉及的文件和写法

**写法要求：**
- 每种扩展场景列出编号步骤，步骤中注明参考文件和行号
- 步骤要具体到"在哪个文件的哪个位置，用什么写法"
- 不写泛泛的"参考现有写法"，要给出真实的参考位置

**示例：**
```
新增 Handler（参考 `handlers/order.ts`）：
1. 在 `handlers/` 下创建 `{name}.ts`，实现 `BaseHandler` 接口（见 `base/handler.ts:8`）
2. 在 `registry/index.ts` 第 23 行的 handlers 数组中追加注册
3. 在 `types/handlers.ts` 补充对应的类型定义（见第 15 行现有写法）
```

## 4. 风险点

**提炼目标：** 不知道就容易出问题的地方，覆盖四类标签，每条一行写入文档。

---

### [技术债]

**如何识别：**
- 明显违反模块内其他约定的写法
- 注释含 `TODO`、`FIXME`、`hack`、`workaround`、`临时`、`暂时`
- 空 catch、类型强制断言（`as unknown as Type`）、硬编码特殊值

**写法：** 三要素：现象 / 原因 / 风险。原因无法推断时写"原因不明，勿擅自修改"。

```
- `payment.ts:67` — [技术债] 现象：catch 为空 / 原因：第三方 SDK 超时抛非致命异常，业务选择忽略 / 风险：补错误处理会中断重试流程
```

---

### [隐式假设]

**如何识别：**
- 入参在使用前未做格式校验，但代码依赖特定格式（长度、类型、范围）
- 函数内部依赖某个外部状态已被设置，但没有显式检查
- 注释或变量名暗示调用顺序（`initialized`、`mustCallFirst`、`afterSetup`）

**写法：** 假设内容 + 违反后的具体后果（不写"可能出错"，写"会发生什么"）。

```
- `store.ts:12` — [隐式假设] init() 必须在任何 get/set 前调用，否则返回 undefined 且不抛错，调用方无感知
```

---

### [副作用]

**如何识别：**
- 函数名看起来是查询或转换，但函数体内有写操作（修改外部变量、emit 事件、写缓存/文件）
- 看似无害的 import 触发了模块级副作用（注册、初始化、订阅）

**写法：** 副作用是什么 + 调用方需要感知什么。

```
- `event.ts:89` — [副作用] formatUser() 看似纯函数，实际会向全局事件总线 emit 'user:read'，影响所有订阅方
```

---

### [测试盲区]

**如何识别：**
- 目录或文件没有对应的 `*.test.*` / `*.spec.*` 文件
- 测试文件存在但明显只覆盖 happy path，边界条件无测试

**写法：** 无覆盖范围 + 改动时需手动验证的具体场景。

```
- `legacy/parser.ts` — [测试盲区] 无任何测试，改动后需手动验证：空输入、嵌套结构、特殊字符三种场景
```

## 5. 文件联动查找方式

**提炼目标：** 确认路径搜索命令在该模块下可用，不枚举具体的联动文件对。

**如何验证：**

```bash
# 按文件路径搜 import 语句（精确，不误伤）
grep -rn "from '.*{目标文件相对路径}'" {模块根}/ --include="*.{ext}"
```

**写到文档：**

将上述命令填入模块实际的根路径和文件扩展名后原样写入文档。AI 在修改代码时按需执行，找到依赖文件后读取并判断是否需要同步修改。

---

## 不写什么

- 通用编程知识或语言语法说明
- 代码质量评价、优化建议
- 文件清单、目录结构说明（可从代码直接观察）
- 无法从代码中直接观察到的推断
- 凭空捏造的示例代码
