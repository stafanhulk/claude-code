# 技术方案指南（阶段 2）

对需求涉及的每个项目，进入其上下文：调研代码 → 澄清 → 复杂度判断 → 生成方案。设计中问出的业务/缘由落知识库（见 knowledge-guide）。

## 一、逐项目推进

需求 `projects` 列多个 → 对每个项目各走一遍下面的流程，各生成一份 `<项目>/docs/design/<需求id>.md`。不同项目改动面不同，方案分别写，禁止合成一份含糊带过。

## 二、调研代码（生成方案前必做）

按需求「涉及项目与改动面」的线索，在目标项目里定位相关代码，逐文件 Read，提炼四件事：

1. **现状如何工作** — 相关流程现在怎么跑通，关键 `文件:行号`。
2. **可复用能力** — 已有同类实现、公共工具、现成 hook / 组件 / 基类（标 `文件:行号`），方案优先复用，不重复造轮子。
3. **约束与坑** — 不变量、隐式假设、改动会牵连的地方。
4. **影响范围** — 改动牵连哪些调用方 / 下游 / 共享状态 / 对外契约（标 `文件:行号`）。

范围不清先 `find` / `grep` 定位再读，禁止只凭文件名推断。

**先加载已有知识库**：调研前先看该项目 `knowledge/` 里有没有相关模块的 KNOWLEDGE.md，就近优先、向上补充作背景（详见 knowledge-guide）。

## 三、澄清到逻辑链条通顺

调研后逐条自检，凡以下情况 MUST 用 AskUserQuestion 提问，禁止猜测或含糊带过：

- 需求意图有歧义，或多种合理理解。
- 边界 / 异常 case 预期行为未知（空数据、超长、并发、多组取哪组）。
- 交互 / 状态流转有未覆盖分支。
- 依赖的前提、约束、外部契约不确定。
- **业务不懂 / "为什么这么设计" 拿不准** —— 这类答案尤其珍贵，问完 MUST 落知识库。

需求文档「待澄清」里的遗留项在这里一并问清。提问可多轮，逻辑链条无断点后才进入下一步。

## 四、复杂度判断与选型

识别关键决策点（有多种合理实现且取舍不同）：

- **简单**（单一合理实现，无关键决策点）→ 直接生成单一推荐方案。
- **复杂**（≥2 个关键决策点）→ 先把每个决策点的「选项 / 取舍 / 推荐」用 AskUserQuestion 或文字列给用户，**拍板后**再展开选定方案。

纯实现细节（变量命名、循环写法）不算决策点，不为凑数硬列。

## 五、知识落盘判定（每次必做,不可静默跳过）

**这一步是流程的必经产出,不是"问出东西才做"的副产物。** 方案完成后 MUST 显式判定一次：本次调研 + 澄清有没有得到值得沉淀进知识库的内容?

判定对象（对照 knowledge-guide「何时写」的判据）：

- 澄清阶段问出的**业务背景 / 隐藏约束 / "为什么这么设计"的缘由** → 值得写。
- 调研中发现的**反直觉约定、不变量、跨模块契约**（读代码不问也能确认但容易踩坑的）→ 值得写。
- 纯"读代码就得到、grep 即得"的模块职责流水账 → **不写**,避免灌水。

三种结果,择一,都要**显式说明**：

| 结果 | 处理 |
|------|------|
| **有可沉淀内容** | 按 knowledge-guide 提议落对应模块 KNOWLEDGE.md,逐段确认后写。 |
| **无隐藏约束,但模块本身值得建档且尚无知识** | 提示"可用 `+kb <模块>` 系统性建",不在 design 里顺手灌。 |
| **无可沉淀内容** | 明说原因（如"需求清晰、未问出隐藏约束,模块职责读码即明"）,跳过,不留空白让人以为漏了。 |

禁止：不做判定、或判定后静默不写也不说明。

## 六、方案文档结构

写入 `<项目>/docs/design/<需求id>.md`（目录不存在则 `mkdir -p`）。核心是**层级树 + 分支枚举**。

```markdown
---
req: <需求id>
project: <项目名>
---

# <需求标题> · <项目名> 技术方案

## 现状
<相关流程现在怎么工作，关键 文件:行号。>

## 设计决策
<若复杂：每个决策点的选型与最终取舍。简单则省略或一句话。>

## 方案
### <功能点A>
1. <有序步骤>
   - **【条件X】**：<行为> → <结果>
   - **【条件Y】**：<行为> → <结果>
2. <步骤>，复用 `<现有函数>`（`文件:行号`）
### <功能点B>
...

## 影响范围
- <牵连的调用方/下游/共享状态/对外契约，标 文件:行号>

## 验收对照
<对齐需求文档的验收标准，人工验收时对照。>
```

写法要点：

- **口吻**：方案是给别人讲、给别人看的对外文档，用专业规范的技术口吻。但专业 ≠ 堆术语——通俗好懂，先讲清是什么/为什么，再给公式或代码。
- **措辞**：禁口语/教程腔（「怎么摆?」「定下来的框长这样」「关键坑」「顶住边不让出去」「一句话」「我们跟着来」「不操心」「费劲」），换中性规范说法（「摆放方式如下」「选区框样式」「注意点」「clamp 不越界」）。决策表「理由」列写技术权衡，不写口白式感受。
- **标题精简**：一级标题不带一长串定语（`# 点图题编辑画板 技术方案`）；子标题短（`3.1 弹窗`，不是「画板这个弹窗怎么弹出来/怎么关掉」）。
- **功能点按归属组织层级**：子功能收进父功能、不平铺。例：绘制/移动/撤销/确认都由工具栏按钮触发 → 收为工具栏节点的子节（3.4.1~3.4.x），讲解时顺功能树往下展开。
- 一层一句短句，靠缩进表达从属，忌长段落。
- 互斥分支用 `**【条件】**：行为 → 结果` 标注，条件列全。
- 所有现有代码引用标 `文件:行号` 且确认真实存在。
- 只设计当前需求，禁止顺手设计未来需求或扩大改动面。

## 七、落盘与输出

- 文件已存在 → 提示用户选 覆盖 / 更新 / 仅预览。
- 落盘后把需求文档 `status` 更新为 `designed`。
- 输出：

```
[方案] <需求id> · <项目名> 已生成：<路径>
       调研文件数：N  形态：单一方案 / 多方案选型
[知识] 已落：<KNOWLEDGE.md 路径列表>
   或   未落：<原因,如 需求清晰未问出隐藏约束>（可选 +kb 系统性建档）
```

多项目需求 → 每项目一行。全部项目方案完成后提示下一步 `/work-flow +dev <需求id>`。
