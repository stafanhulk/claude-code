# 知识库指南（设计与开发阶段共用）

知识库帮 AI 读懂项目代码、降低踩坑。核心价值是**读代码得不到的隐藏约束**——用户对业务、"为什么这么设计"的解答。

## 一、映射规则：镜像目标项目源码树

每个项目在自己目录下维护 `knowledge/`，路径镜像源码树，一个模块一份、与源码目录一一对应：

```
project1/src/auth/          →  project1/knowledge/src/auth/KNOWLEDGE.md
project1/src/pay/wechat/    →  project1/knowledge/src/pay/wechat/KNOWLEDGE.md
跨模块业务链路             →  project1/knowledge/_flows/<名称>.md
```

- 模块级查找纯靠路径推导，零索引维护。判断某模块有无知识：`test -f <项目>/knowledge/<路径>/KNOWLEDGE.md`。
- 文件名固定 `KNOWLEDGE.md`（避开与真实 `README.md` 撞车）。
- 跨模块知识（穿多个目录、横切契约、状态机——知识边界 ≠ 目录边界）无归属目录 → `knowledge/_flows/<名称>.md`，frontmatter `involves` 声明涉及模块。
- **一个需求可能横跨多个项目**：各项目**自己那部分**的知识落进各自项目的 `knowledge/`，禁止把 A 项目的模块知识写进 B 项目。
- **跨项目的业务链路知识**（如"下单前端 → 订单后端"的契约、字段对齐、失败回滚——边界跨越项目）无处归属单个项目，按下面优先级选落点，frontmatter `involves` 列涉及的项目与模块：
  - 若工作区里有专门的**业务知识库项目**（团队集中沉淀业务知识的项目）→ 优先落到该项目中，随它一起进 git 共享。
  - 否则落**工作区级** `<工作区根>/knowledge/_flows/<名称>.md`（与 `requirements/` 同级）。

### 一个文件含多个业务功能怎么梳理

**核心原则：知识按「业务功能」组织，不按「文件」组织。** 文件是物理载体，功能才是知识边界。一个大文件（如 `src/order/index.ts` 塞了下单、退款、评价三块）不拆成三份知识文件——仍按所在目录落一份 `KNOWLEDGE.md`，但在文件**内部按功能切段**，各段用**入口方法名**锚回代码：

```markdown
## 关键逻辑与缘由
### 下单（`createOrder`）
- 预扣和落单必须同一事务（`createOrder` 内），否则超卖
### 退款（`refundOrder`）
- 只认已支付状态，未支付订单退款直接拒（`refundOrder` 开头的状态校验）
```

要点：

- **用功能小标题 + 入口方法名**（`### 功能名（方法名）`）把一个文件的多块能力分开描述，读的人靠方法名就能在文件里定位，代码增删行不受影响。
- **每块功能各自记业务含义/缘由/雷区**，不要把三个功能的规则混在一段里，否则又变回流水账。
- **判断该不该拆成多个模块**：若这几块功能其实职责独立、只是历史原因塞一个文件 → 知识照实按功能分段记，同时在「雷区与存疑」标注"建议拆分"，是否真拆由用户定，知识库不擅自假设重构。
- **一个功能横跨多文件**（比 grep 更常见）→ 走 `_flows/<功能>.md`，`involves` 列相关文件所在模块，正文按调用时序串起散落各文件的片段。

## 二、何时写知识库（三条路径）

不是所有信息都进知识库。判据：**「帮 AI 读懂这块代码在干什么、为什么这么写」→ 写；一次性的实现细节、grep 即得的事实 → 不写。**

| 路径 | 触发 | 时机 |
|------|------|------|
| **设计阶段（被动）** | `+design` | 向用户问出的业务背景、隐藏约束、"为什么这么设计"的缘由 —— 最该写。 |
| **开发阶段（被动）** | `+dev` | 读码/改码时又问出的新隐藏约束，或发现已有知识与代码现状对不上（已过时）。 |
| **主动构建** | `+kb <项目\|模块>` | 脱离需求,主动读一个模块的代码 + 问用户,系统性建/补该模块知识（见下「六、主动构建」）。 |

被动两条是需求流程的副产物；主动一条用于新接手项目、想提前沉淀某块业务。

## 三、KNOWLEDGE.md 结构

**只记「读代码得不到」的东西。** 判据：一个看得懂代码的工程师，不看这条会不会照样搞错 / 白踩坑?会→记;不会→删。四个桶依次是：先让人落地（定位），再补代码里没有的外部知识（业务含义、关键逻辑与缘由），最后兜底（雷区与存疑）。

| 章节 | 回答什么 | 取舍 |
|------|---------|------|
| frontmatter | 这是哪个模块、覆盖哪些关键词 | 只写 `module`/`covers`，供路径推导与检索，不写时间戳 |
| **定位** | 这个模块用来做什么、边界、从哪进 | 刻意薄，1-2 句划边界 + 入口文件。做薄本身就是防流水账 |
| **业务含义** | 含义不清的变量/字段/枚举/术语 = 业务里的什么概念 | 符号 ↔ 业务概念的翻译（`status=3` → 已核销）。读代码得不到，纯外部知识 |
| **关键逻辑与缘由** | 某段逻辑为什么这么写、解决什么问题 | 业务向、技术向的缘由都装。只记非显然的，代码一眼能懂的不写 |
| **雷区与存疑** | 改不了但不知为啥 / 彻底说不清 | 与上一桶错开：那桶是「知道为什么」，这桶是「不知道为什么但重要」 |

**排序固定**，多文件/多功能时在各桶内部按功能切段（见第一节「一个文件含多个业务功能」）。**桶可省不可乱**——某模块没雷区就省掉「雷区与存疑」，但别把不知缘由的东西硬塞进「关键逻辑与缘由」。

```markdown
---
module: src/auth              # 相对项目根的模块路径（_flows 用 involves 代替）
covers: [登录, 鉴权, token刷新]  # 这份知识覆盖的关键词
---

## 定位
<这个模块用来做什么，一两句划边界（含什么、不含什么）+ 从哪个文件进。>

## 业务含义
<把含义不清的字段/枚举/术语翻译成业务概念。>
- `status=3` → 已核销；`type=2` → 企业用户

## 关键逻辑与缘由
<某段逻辑为什么这么写、解决什么问题。业务向+技术向都可。>
- <逻辑/写法>，为了 <解决什么问题>（缘由：用户说明；位置：`<方法名>` 中）

## 雷区与存疑
<改不了但不知为啥的红线（记「改会怎样」+ 追查断点），或彻底说不清的现象。>
- ⚠️ <红线>，改会 <后果>，不知为什么（追查：问过谁 / 查到哪 / 为何断头）
```

跨模块 `_flows/<名称>.md` 用 `involves: [src/a, src/b]` 代替 `module`，正文写跨模块调用时序 / 契约 / 失败回滚。`_flows/` 的重心是**模块之间**——时序、契约（关联键/幂等）、失败回滚、跨模块的不变量；单模块内部细节仍留在各自 `KNOWLEDGE.md`，不重复。

## 四、写作纪律

- **只记读代码得不到的**：业务含义、缘由、雷区。禁止编造，关键断言用**方法名/符号名**锚定（如「`formatOutputValue` 方法中」）。
- **断言式表达**。禁止：①统计式计数（"N 个函数"，零信息量、加一个就过时）；②模糊限定词（可能/大约/通常）；③流水账复述执行过程（"先调A再调B"读代码就有）。
- **用户解答是核心来源**：业务含义、缘由多半读代码得不到，靠问用户。落盘注明缘由来源（用户口述 / 关联方法名或符号名）。
- **缘由未知的红线 MUST 记全三件事**：①红线是什么 ②改会怎样（实证，比"据说不能改"值钱）③追查断点（问过谁/查到哪/为何断头），标 `⚠️`。禁止因说不清就当普通代码或不记。
- 彻底说不清的 → 落「雷区与存疑」，如实记现象，禁止猜一个填进去。
- **禁止用行号定位，一律用方法名/符号名**：行号代码一改就错、极易过时。定位统一写「`<方法名>` 方法中」「`<常量名>` / `<枚举名>`」这类符号锚，如「`formatOutputValue` 方法中做了兜底」。需要指到文件时写文件名即可，不带 `:行号`。

## 五、落盘规则

- **先提议再落盘**：整理成草案，逐桶（定位 → 业务含义 → 关键逻辑与缘由 → 雷区与存疑）与用户确认，确认后才写。用户不想落盘则不强写。
- frontmatter 只写 `module`/`covers`（或 `involves`/`covers`），不写 `updated`/`source`（新鲜度从 git 反推）。
- 已存在 KNOWLEDGE.md → 只改与代码现状对不上的章节，无变化章节原样保留（怎么定位见 dev-guide）。

## 六、主动构建（+kb）

脱离需求,系统性为某项目/模块建知识库。**按模块逐个建,禁止整项目一次全建**（一次读太多必然浮于表面、编造风险高）。

0. **首次为该项目建库 → 写知识库加载约定**：先用 AskUserQuestion 问「个人配置 or 共享配置」——
   - **个人配置**：目标文件 `<项目>/CLAUDE.local.md`，并确保 `<项目>/.gitignore` 含 `CLAUDE.local.md`（不进 git，只你本地生效）。
   - **共享配置**：目标文件 `<项目>/CLAUDE.md`（进 git，团队共享）。

   检测目标文件有无约定块（`grep -q "KNOWLEDGE-BASE:START" <目标文件>`）。没有 → 征得用户同意后追加约定块（模板见第七节）。已有则跳过。
1. **定位目标**：
   - 入参是**项目名** → 列该项目顶层模块清单（源码目录），让用户选先做哪几个模块,不要贪多。
   - 入参是**模块路径** → 直接对该模块。
2. **对每个模块**：
   - 逐文件 Read 核心源码,禁止只凭文件名/目录推断。
   - 按四桶提炼：定位 / 业务含义 / 关键逻辑与缘由 / 雷区与存疑,关键断言用方法名/符号名锚定（禁止行号）。
   - 看不懂/反直觉/"为什么这么设计"、含义不清的字段 → AskUserQuestion 问用户,答案落「业务含义」或「关键逻辑与缘由」；改不了但不知为啥的落「雷区与存疑」并记全三件事；彻底说不清的如实记现象。
   - 按第三节结构整理草案,逐段与用户确认后写 `<项目>/knowledge/<模块路径>/KNOWLEDGE.md`。
3. **跨模块链路** → 落 `knowledge/_flows/<名称>.md`,`involves` 声明涉及模块。
4. **收尾**：输出已建/更新清单 + 建议下一个待建模块,让用户决定是否继续。

与被动路径的唯一区别是**入口和范围**（主动圈定模块、成批建）；写作纪律、映射规则、先提议再落盘全部照旧。

## 七、知识库加载约定块（写入 CLAUDE.local.md 或 CLAUDE.md）

`+kb` 首次为某项目建库时，往目标文件追加下面的约定块，让 Claude 每次进该项目自动知道知识库在哪、怎么读、怎么更新。目标文件按 step 0 问出的选择：

- **个人配置** → `<项目>/CLAUDE.local.md`，并确保 `<项目>/.gitignore` 含 `CLAUDE.local.md`（不进 git，只本地生效）。
- **共享配置** → `<项目>/CLAUDE.md`（进 git，团队共享）。

约定块用可识别的起止标记包裹，便于后续更新时定位替换：

约定块写成**编码规范硬规则**（MUST / 禁止式，可直接照做），不写成松散介绍让 Claude 自己解读：

```markdown
<!-- KNOWLEDGE-BASE:START -->
## 知识库使用规范（knowledge/）

本项目在 `knowledge/` 维护镜像源码树的知识库，只记「读代码得不到」的业务含义、设计缘由、雷区。以下为强制规范：

**位置映射（固定）**：源码 `src/<模块>/` ↔ 知识 `knowledge/src/<模块>/KNOWLEDGE.md`；跨模块链路在 `knowledge/_flows/<名称>.md`。查某模块有无知识：`test -f knowledge/<路径>/KNOWLEDGE.md`。

**读代码前 MUST**：
1. 动某块代码前，先按上面映射查对应 KNOWLEDGE.md，存在则 MUST 先 Read 作背景，就近优先、向上补充（子模块细节 > 父模块概览）。
2. 重点看「业务含义」「关键逻辑与缘由」「雷区与存疑」——那是读代码得不到的。标 `⚠️` 的雷区禁止擅自改动。

**改代码后 MUST**：
1. 若改动使某 KNOWLEDGE.md 记录的内容（业务规则 / 缘由 / 雷区 / 涉及的方法）不再准确，MUST 主动提议更新对应文件——**只提议，用户确认后才写**，禁止擅自落盘。
2. 只改与代码现状对不上的章节，没变的原样保留。
3. 读码或问用户得到新的业务含义 / 设计缘由 / 雷区时，同样提议补进对应 KNOWLEDGE.md。

**写知识时 MUST**：只记读代码得不到的业务含义、缘由、雷区；关键断言用方法名/符号名锚定（如「`formatOutputValue` 方法中」），**禁止用行号**。禁止：编造、流水账复述执行过程、统计式计数、模糊限定词。
<!-- KNOWLEDGE-BASE:END -->
```

- **只提议不擅自写**：追加约定块前先征得用户同意（改 CLAUDE.local.md / CLAUDE.md 属落盘）。
- **已有约定块**（`grep -q "KNOWLEDGE-BASE:START"`）→ 跳过，不重复追加；内容需更新则替换标记之间的部分。
- 个人转共享：把整块从 `CLAUDE.local.md` 挪到 `CLAUDE.md` 并从 `.gitignore` 移除即可（反之亦然）。
