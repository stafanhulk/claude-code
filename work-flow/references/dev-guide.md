# 开发指南（阶段 3）

按技术方案开发，开发中持续更新知识库，结果交人工验收。

## 一、按方案开发

0. **入参路由 + 置 dev 态**：按 SKILL.md 阶段3 的路由判断怎么进（有方案/仅需求文档跳过设计/找不到提示先设计/自由文字普通开发）。正式开始开发时，把需求文档 `projects` 里当前项目状态置 `dev`（自由输入无需求文档则跳过）。
1. **读方案**：Read `<项目>/docs/design/<需求id>.md`，逐功能点实现。方案是准绳，偏离方案（发现方案有问题需调整）MUST 先说明再改，禁止默默偏离。
2. **贴合项目约定**：复用设计阶段确认的现有能力（函数/工具/组件），匹配项目现有代码风格、命名、目录结构，禁止引入新范式或新依赖（需新依赖先问）。
3. **多项目需求**：`projects` 有多个 → 逐项目按各自方案开发。跨项目契约（接口字段、协议）改动 MUST 两端对齐。
4. **调试纪律**：先复现再修，定位根因；禁止 try/catch 吞错或注释断言绕过问题。
5. **改了行为跑相关测试**；禁止为通过测试而弱化断言或 mock 实现细节。

## 二、持续更新知识库

开发中知识库会与代码现状对不上（过时），或长出新知识，MUST **提议更新**（只提议不擅自落盘，用户确认后写）：

**触发更新的两种情况：**

| 情况 | 处理 |
|------|------|
| **记录过时**（代码变了、知识没跟上） | 改动的代码正好是某 KNOWLEDGE.md 记录过的模块，且改动使原描述（业务含义/缘由/雷区/涉及的方法）不再准确 → 定位到具体桶，提议更新，无关章节原样保留。 |
| **长出新知识** | 开发中读码 / 问用户又得到新的隐藏约束、业务缘由 → 按 knowledge-guide 补进对应模块的 KNOWLEDGE.md（模块无知识文件则新建）。 |

**怎么定位过时内容**：用 `git diff` 看本次改了哪些文件 → 反查这些路径对应的 `knowledge/<路径>/KNOWLEDGE.md` 是否存在 → 存在则比对记录内容与新代码，只改真正变化的章节。

**节奏**：不在编码中途频繁打断。可在一个功能点告一段落、或需求开发完成后统一提议知识更新，逐段与用户确认。

**知识更新判定（每次开发收尾必做,不可静默跳过）**：需求开发完成后 MUST 显式判定,并用下面这个**固定醒目的独立块**输出——**放在本次回复最末尾、单独成块**，不许混在开发总结的段落里（那样每次都被淹没看不到）：

```
━━━━━━ 📚 知识库检查 ━━━━━━
本次改动涉及模块：<模块>
判定结果：<有过时/新知识 | 无需更新>
→ <有：提议更新 <KNOWLEDGE.md 路径> 的 <章节>，待你确认；
   无：原因（如"改动未触及已记录模块、未问出新约束"）>
━━━━━━━━━━━━━━━━━━━━
```

- **每次都要出这个块**，无论有没有更新——「无需更新」也要显式出现，让你确认它真判过、不是漏了。
- 有更新 → 块里点明改哪个文件哪个章节，**只提议，用户确认后才写**。
- 禁止：不做判定、把结论塞进普通段落、或有过时内容却静默不提。

## 三、遇到不懂继续问

开发中若碰到设计阶段没覆盖的业务疑点、反直觉代码、"为什么这么设计"，仍 MUST 用 AskUserQuestion 问用户，答案落知识库（见 knowledge-guide）。禁止猜。

## 四、编写单元测试（条件化，非必须）

**本步只做单元测试。** 集成测试 / e2e 不在这里——那需要后续单独拆分，依靠 playwright、chrome-devtools 等工具配合，不在本步范围。

**先探测项目有无单测机制，有才写；没有则不硬塞框架。**

探测（按项目类型看）：

| 类型 | 探测信号 |
|------|---------|
| 前端 | `package.json` scripts（`test`/`vitest`/`jest`）、测试目录（`__tests__`/`*.test.*`/`*.spec.*`）、配置（`vitest.config`/`jest.config`） |
| 后端 Java | `pom.xml`/`build.gradle` 里 JUnit 依赖、`src/test/java` 目录 |
| 后端 Go | `*_test.go` 文件、`go test` 可用 |
| 后端 Python | `pytest`/`unittest`、`tests/` 目录、`test_*.py` |

| 情况 | 处理 |
|------|------|
| **项目已有单测机制** | 为本需求改动的行为补单元测试，贴合项目现有写法（同款框架、目录、命名、断言风格）。跑通,失败则定位根因修复,禁止弱化断言或 mock 实现细节凑过。 |
| **项目无单测机制** | 不为单个需求擅自引入测试框架。如实告知"该项目无单测机制,跳过"。用户明确要求搭建时才引入(先问选型)。 |

多项目需求 → 各项目按各自情况分别判断,一个有一个没有很正常。

## 五、人工验收

- 实现完成后，skill **不自行判定验收通过**。列出「已实现的功能点 + 对照需求文档验收标准」，交人工验收。
- 跑得动的自检（构建/lint/相关测试）先跑，把结果如实报给用户，失败则定位根因修复（禁止 `--no-verify` 或跳过）。
- 人工确认通过后，在需求文档 `projects` 里把**当前开发的这个项目**状态置 `done`（如 `订单后端(done)`），不碰其他项目状态。全部项目 `done` 需求才算整体完成。
- **整体完成后提示清理**：该需求全项目 `done` 后，提示用户手动删除对应需求文档（或整批做完删掉 `requirements/<日期>/` 文件夹），避免需求文档越堆越多。只提示，删不删由用户定，skill 不擅自删。

## 六、输出

```
[开发] <需求id> 已实现
  项目 project1：<改动摘要>  自检：<构建/测试结果>
  项目 project2：<改动摘要>
[单测] project1：<用例数 / 结果>  project2：无单测机制,跳过
待人工验收：对照 requirements/<日期>/<需求id>.md 的验收标准
```

**紧接着 MUST 单独输出「📚 知识库检查」醒目块（格式见第二节），放在整个回复最末尾**，不与上面的开发总结混排——这样知识库提示每次都拎得出来、不被淹没。

## 七、小步快跑提交

**开发中每写完一个完整功能 / 模块（一个可独立成立的改动单元），就主动提示用户提交一次 git。** 不要攒到需求全做完才一次大提交。

- **主动提示,用户确认才提**：给出建议的提交范围(哪些文件)和 commit message 草稿,等用户点头再执行；用户说"先不提"则继续开发,禁止自动提交。
- **提交粒度 = 一个完整功能/模块**：能独立说清"这次提交做了什么"即可切一刀。宁可多个聚焦提交,不要大杂烩。
- 按项目分别提交,需求文档 / 方案 / 知识库与代码可分开聚焦提交。
- commit message 用 conventional commits（`feat:`/`fix:`/`refactor:` 等），正文写"为什么"。
- 按文件名 `git add`，禁止 `git add .`（避免误提交 `.env`/临时文件/IDE 配置）。破坏性操作（`reset --hard`/`push --force`/跳 hook）先确认。
