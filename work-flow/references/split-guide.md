# 拆需求指南（阶段 1）

抓取文档 → 拆成一个个独立需求 → 每需求一份 md。

## 一、抓取文档

先判定来源，再抓：

| 来源 | 判定 | 抓取方式 |
|------|------|---------|
| 本地文档 | 入参是存在的 `.md` 文件路径 | `Read` 工具直接读 |
| 飞书文档 | 入参含 `feishu.cn` / `larksuite` / 形如文档 URL | `lark-cli docs +fetch --api-version v2 --doc "<url>"` |
| 判不准 | 既不是本地文件也不像飞书链接 | AskUserQuestion 问用户来源，禁止猜 |

```bash
# 本地判定
[ -f "<入参>" ] && case "<入参>" in *.md) echo "本地 md";; esac

# 飞书抓取
lark-cli docs +fetch --api-version v2 --doc "<文档URL或token>"
```

飞书 fetch 失败（未登录/无权限）→ 如实报错并提示用户 `lark-cli auth login`，禁止编造文档内容。

## 二、拆分粒度

**一个需求 = 一件可以单独设计方案、单独开发、单独验收的事。**

拆分判据：

- **按功能点拆**，不按文档章节机械切。一个章节可能含多个需求，多个零散段落可能属同一需求。
- **可独立交付**：拆出来的每条能单独走「设计 → 开发 → 验收」而不强依赖另一条完成。
- **粒度适中**：太粗（"重构整个后台"）无法设计，太细（"改个按钮文案"）不值得单独立档。拿不准粒度就把候选拆分列给用户确认。

**按前后端拆**：一个功能常横跨前端与后端（前端交互/展示 vs 后端接口/数据/逻辑），二者天然是不同功能点、对应不同项目。拆分时把前后端职责分清,分别落到各自项目：

- 若前后端可各自独立开发验收（如接口先定契约,前后端并行）→ 拆成前端需求、后端需求两条,各自 `projects` 指向对应项目。
- 若耦合紧、必须一起验收 → 仍是一个需求,但在「涉及项目与改动面」里把前端做什么、后端做什么分开写清。

**大功能拆成小功能点（便于多人协作）**：一个大功能要改多个部分时,按可独立交付的功能点拆成多个小需求,让不同人可并行认领。拆分时标注功能点之间的依赖顺序（谁挡谁）,避免拆完互相死等。

- **横跨项目本身不是拆分理由**：一个需求即使改动多个项目（前端+后端、多个前端），只要是一件不可再分的事,仍是一个需求（`projects` 列多个）。要拆的是「可独立交付的功能点」,不是「项目数」。

拆完先把「需求清单（id + 标题 + 涉及项目 + 功能点依赖关系）」列给用户过一眼，再逐份落盘。

## 三、定位涉及项目

基于 `+init` 探测出的真实候选项目（父目录下的子目录,含前端与后端）判断：

1. 从需求描述里的功能/页面/模块/接口关键词，对候选项目名、目录结构做匹配。前端功能 → 前端项目,后端接口/数据/逻辑 → 后端项目。
2. 匹配不确定时用 `grep` / `find` 到候选项目里搜关键词佐证，禁止仅凭项目名猜。
3. 仍判不准 → AskUserQuestion 让用户指定该需求涉及哪些项目。

`projects` 只填真实存在的目录名。

## 四、需求文档模板

写入 `requirements/<需求id>.md`。`<需求id>` 用 kebab-case 短标识（如 `login-sso`、`order-export`）。

```markdown
---
id: <需求id>
title: <一句话需求标题>
projects: [project1, project2]     # 涉及的项目名，来自父目录真实子目录
source: <本地文档路径 | 飞书URL>    # 需求出处，便于回溯
status: split                      # split / designed / dev / done，由各阶段推进
---

## 背景
<为什么要做这个需求，业务动机。抓取文档里有则提炼，没有留空待澄清。>

## 需求描述
<要做成什么样。分条列清楚功能点与预期行为。>

## 涉及项目与改动面
- **project1**：<在这个项目里大致要动什么（模块/页面）>
- **project2**：<...>

## 验收标准
<人工验收时对照什么判定完成。可列 checklist。>

## 待澄清
<拆分时发现的歧义、缺失信息，留给设计阶段问用户。>
```

- `status` 字段是阶段推进的锚：拆分完 `split`，方案完成 `designed`，开发中 `dev`，验收通过（人工确认后）`done`。
- 抓取文档信息不全时，**不要编造**背景/验收，写进「待澄清」，设计阶段再问。

## 五、落盘与输出

- 每份需求写 `requirements/<需求id>.md`。已存在 → 提示用户选 覆盖 / 更新 / 仅预览。
- 全部落盘后输出：

```
[拆分] 来源：<文档>  拆出 N 个需求
  - <id1>  <标题>  → projects: [..]
  - <id2>  <标题>  → projects: [..]
下一步：/work-flow +design <需求id>
```
